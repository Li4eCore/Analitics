# XYZ-анализ через коэффициент вариации

> Разбор материала курса ["ABC-XYZ анализ в SQL"](https://stepik.org/course/197644/syllabus)
> на Stepik — конспект логики, не самостоятельно решённая задача.

В отличие от ABC-анализа (делит товары по **объёму/сумме** продаж), XYZ-анализ
делит товары по **стабильности спроса** — насколько предсказуемо ведут себя
продажи месяц к месяцу. Часто используется вместе с ABC для полной картины
управления ассортиментом (матрица ABC-XYZ).

---

## Ключевая идея — коэффициент вариации (CV)

```
CV = стандартное отклонение / среднее значение
```

- **Стандартное отклонение** — насколько сильно продажи "прыгают" вокруг
  своего среднего значения по месяцам (абсолютная величина)
- **Деление на среднее** превращает это в **относительный** показатель —
  так можно сравнивать товары с разными объёмами продаж между собой
  (иначе товар с большими продажами всегда выглядел бы "нестабильнее"
  просто из-за масштаба цифр)

**Правило простое:** чем меньше CV, тем стабильнее и предсказуемее спрос.

Пример из задания — наглядно показывает суть:
- Пицца "A": продажи `[100, 105, 98, 102, 101]` → CV ≈ 2.6% → **стабильно**
- Пицца "B": продажи `[20, 150, 5, 80, 45]` → CV ≈ 97% → **хаотично**

---

## Пороги классификации

| Категория | Условие | Смысл |
|---|---|---|
| **X** | CV ≤ 0.1 (10%) | стабильный спрос, легко прогнозировать |
| **Y** | 0.1 < CV ≤ 0.12 (10–12%) | умеренная нестабильность |
| **Z** | CV > 0.12 (>12%) | нестабильный, сложно прогнозировать |

Пороги условны и подбираются под задачу — 0.1/0.12 не единственно верные
значения, курс предлагает более строгий (0.05/0.1) и более мягкий (0.1/0.2)
варианты в зависимости от специфики бизнеса.

## Полный запрос

```sql
WITH sales_by_month AS (
    SELECT
        name AS pizza_name,
        TO_DATE(month_year, 'DD.MM.YYYY') AS sale_month,
        SUM(quantity) AS monthly_quantity
    FROM pizza_sales
    WHERE year = 2015
    GROUP BY name, TO_DATE(month_year, 'DD.MM.YYYY')
),
variation_calculation AS (
    SELECT
        pizza_name,
        STDDEV_POP(monthly_quantity) AS standard_deviation,
        AVG(monthly_quantity) AS average_quantity,
        ROUND(
            STDDEV_POP(monthly_quantity) / AVG(monthly_quantity),
            5
        ) AS variation_coefficient
    FROM sales_by_month
    GROUP BY pizza_name
)
SELECT
    pizza_name,
    variation_coefficient,
    CASE
        WHEN variation_coefficient <= 0.1 THEN 'X'
        WHEN variation_coefficient <= 0.12 THEN 'Y'
        ELSE 'Z'
    END AS xyz_category
FROM variation_calculation
ORDER BY xyz_category, pizza_name;
```

**По шагам:**

1. **CTE `sales_by_month`** — сворачивает продажи до одной строки на товар
   на месяц (нужна именно такая гранулярность — по месяцам, а не по дням
   и не по годам целиком, потому что вариация считается **между месяцами**).
2. **CTE `variation_calculation`** — по каждому товару считает стандартное
   отклонение и среднее по его 12 (или сколько есть) месячным значениям,
   затем делит одно на другое — получает сам коэффициент вариации.
3. **Финальный SELECT** — просто раскладывает по трём категориям через `CASE`,
   по тем же порогам, что в ABC-анализе, только категории называются X/Y/Z,
   а не A/B/C, и смысл противоположный по духу: тут речь про предсказуемость,
   а не про важность/вклад в выручку.

---

## Важный нюанс — почему именно STDDEV_POP, а не STDDEV_SAMP

В SQL обычно есть два варианта стандартного отклонения:
- `STDDEV_POP()` — генеральная совокупность (делит на N)
- `STDDEV_SAMP()` — выборочное (делит на N-1)

Если у товара мало наблюдений (например, всего 5 месяцев), разница между
ними может быть заметной. `STDDEV_POP` уместен, когда рассматриваемые
месяцы — это **вся** интересующая нас совокупность (весь 2015 год целиком),
а не выборка из более широкого периода.

---

## Почему считают по количеству (quantity), а не по выручке

Выручка может колебаться из-за изменения цены или акций, даже если
реальный спрос (сколько единиц покупают) стабилен. Количество —
более чистый индикатор именно **стабильности спроса**, а не ценовой политики.
