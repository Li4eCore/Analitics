# Модель данных в Power BI

Конспект по модулю курса [Microsoft Power BI, Power Query, DAX](https://stepik.org/course/190679).

---

## Что такое модель данных

Модель данных — структурированный набор связанных таблиц. Состоит из:
- **Tables** (таблиц) — сами данные
- **Relationships** (связей) — соединения между таблицами по общим полям

**Ключевая идея:** без связи Power BI воспринимает таблицы как полностью
независимые — например, матрица "категория → количество товаров" без
связи покажет **одно и то же общее число** во всех строках, а не разбивку
по категориям, потому что Power BI не может сопоставить строки одной
таблицы со строками другой.

---

## Связи вместо физического объединения (Merge)

`Merge Queries` в Power Query физически сливает таблицы в одну широкую.
Для модели данных **предпочтительнее связи**, а не merge:

| Причина | Почему это важно |
|---|---|
| Эстетика | модель со связями нагляднее одной гигантской таблицы |
| Эффективность | таблицы хранятся отдельно, соединяются "виртуально" на лету |
| Гибкость | легко добавлять новые таблицы без пересборки всей структуры |
| Навигация | удобнее работать с отдельными логическими сущностями |

---

## Ключи: Primary Key и Foreign Key

- **Primary Key (PK)** — уникально идентифицирует каждую запись
  (`categories_dir.category_id`)
- **Foreign Key (FK)** — ссылается на PK другой таблицы
  (`products_dir.category_id`)

Связь строится именно по общему столбцу-ключу.

---

## Три способа создать связь

1. **Перетаскивание** во вкладке `Model` — зажать столбец в одной
   таблице и перетащить на одноимённый столбец в другой
2. **Через `Modeling → Manage relationships → New...`** — выбрать
   Table 1 (From) и Table 2 (To) явно из выпадающих списков
3. **Autodetect** — Power BI сам ищет связи по совпадающим именам
   столбцов и типам данных; удобно для старта, но результат нужно
   обязательно проверять руками

---

## Настройки связи

| Параметр | Что определяет | Значение по умолчанию для справочник→факты |
|---|---|---|
| **Cardinality** | тип отношения между таблицами | `One to many` — самый частый случай |
| **Cross filter direction** | в какую сторону идут фильтры | `Single` — только от "один" к "многие" |
| **Make this relationship active** | связь используется по умолчанию | включено (между парой таблиц активна только одна) |
| **Assume referential integrity** | оптимизация для больших моделей | опционально, требует уверенности в целостности данных |

---

## Типы кардинальности

| Тип | Обозначение | Смысл |
|---|---|---|
| **One to many** | `1 → *` | одна запись слева ↔ много справа (самый частый) |
| **Many to one** | `* → 1` | та же связь, взгляд с другой стороны |
| **One to one** | `1 → 1` | редко, обычно при разделении таблицы на части |
| **Many to many** | `* → *` | требует особой настройки, риск неоднозначностей — избегать |

## Справочники vs таблицы фактов

**Справочники (dimension tables)** — статичные сущности: товары, клиенты,
сотрудники, категории. Обычно мало FK (0-2), их роль — хранить описания.

**Таблицы фактов** — фиксируют события, каждая строка — транзакция.
Содержат **много FK**, привязывающих событие к разным справочникам:

```
orders_total (таблица фактов)
├── order_id       PK
├── customer_id    FK → customers
├── employee_id    FK → employees
├── ship_via       FK → shippers
```

Одно событие ("заказ") одновременно затрагивает несколько справочников —
поэтому у таблицы фактов много внешних ключей.

---

## Автоматическая фильтрация через активную связь

Когда есть активная связь `categories_dir[category_id] → products_dir[category_id]`,
добавление `category_name` в строки матрицы и `Count of product_id` в
значения автоматически фильтрует товары по каждой категории отдельно —
без единой написанной формулы. Это ключевой механизм Power BI.

Без связи — во всех строках одно и то же общее число (нет контекста фильтрации).

---

## Неактивные связи и USERELATIONSHIP

**Ограничение:** между двумя таблицами может быть только **одна активная**
связь. Если у таблицы фактов два поля дат (например, `order_date` и
`shipped_date`), обе логически ссылаются на календарь — но активной
может быть только одна.

**Решение:** вторая связь создаётся, но без галочки "Make this
relationship active" — она становится **неактивной** (пунктирная линия
в Model View) и не участвует в фильтрации, пока её явно не вызовут.

**Активация неактивной связи внутри меры DAX:**
```dax
Shipped_Orders =
CALCULATE(
    COUNTROWS('orders_total'),
    USERELATIONSHIP('calendar'[date], 'orders_total'[shipped_date])
)
```

| Часть формулы | Роль |
|---|---|
| `CALCULATE(...)` | меняет контекст фильтрации для вычисления |
| `COUNTROWS('orders_total')` | считает строки в изменённом контексте |
| `USERELATIONSHIP(...)` | временно включает конкретную неактивную связь |

После вычисления меры связь снова становится неактивной — временная
активация действует только внутри этой одной меры, не меняя модель в целом.

**Результат:** в одной матрице можно одновременно показать "заказано по
году" (через активную связь `order_date`) и "отгружено по году" (через
меру с `USERELATIONSHIP` по `shipped_date`).

## Направление фильтрации: Single vs Both

**По умолчанию — Single (однонаправленная):** фильтр идёт только от
таблицы на стороне "один" (справочник, PK) к таблице на стороне "многие"
(факты, FK). В обратную сторону фильтр **не проходит**.

**Пример проблемы:** если взять `employee_id` из таблицы фактов
`orders_total` (а не из справочника `employees_dir`) и попытаться
вывести рядом количество территорий из связанной таблицы —
результат будет **неверным**: везде одно и то же общее число, потому
что фильтр не может "пройти назад" через цепочку связей.

**Правильный подход:** для фильтрации, группировки и подписей всегда
брать поля **из справочников**, а не из таблиц фактов. Это быстрее
(меньше уникальных значений для обработки) и логичнее по смыслу.

**Принцип "сверху вниз":** справочники располагать выше в модели,
таблицы фактов — ниже, поток фильтрации течёт сверху вниз.

---

## Двунаправленная фильтрация (Both) — когда и почему опасна

Включается через `Edit relationship → Cross filter direction → Both`.
Позволяет фильтру идти в обе стороны — решает проблему выше, но ценой:

| Риск | В чём проблема |
|---|---|
| Раздувание данных | одни и те же строки могут учитываться несколько раз |
| Потеря данных | конфликтующие фильтры "гасят" друг друга |
| Производительность | движок анализирует все возможные пути фильтрации |
| Сложность отладки | сложно понять, почему визуал показывает именно эти числа |
| Поддержка | другим аналитикам сложно разобраться в логике отчёта |

**Лучшие альтернативы Both:**
1. Фильтровать через справочники (см. выше)
2. Добавить нужные поля из справочника прямо в таблицу фактов через
   Power Query (один раз на этапе подготовки данных)
3. Написать отдельную меру DAX под конкретный расчёт

**Both можно рассматривать** только если модель совсем простая (2-3
таблицы), логика полностью понятна, все итоги проверены, и отчётом
пользуешься только ты сам.

## Скрытие полей в Report View

**Как скрыть:** в панели `Fields` клик по значку глаза рядом с полем,
или правой кнопкой → `Hide in report view`. Можно скрыть отдельное поле
или целую таблицу целиком.

**Важно:** скрытие поля не удаляет его из модели — оно по-прежнему
доступно для связей и вычислений, просто не видно пользователю в
интерфейсе построения визуалов.

**Что стоит скрывать:**
- Внешние ключи в таблицах фактов (`category_id` в `products_dir`) —
  пользователь не должен случайно фильтровать по ним вместо справочника
- Технические ID, если есть текстовое название-аналог
- Промежуточные/служебные столбцы

**Почему это влияет на производительность, не только на удобство:**

| Сценарий | Что происходит |
|---|---|
| Фильтр по `category_id` из `products_dir` (77 строк) | Power BI проверяет 77 значений, хотя уникальных категорий всего 8 |
| Фильтр по `category_id` из `categories_dir` (8 строк) | Power BI проверяет только 8 значений — быстрее |

Внешние ключи в фактах содержат много повторов — фильтрация по ним
менее эффективна, чем по уникальным значениям в справочнике.

## Итоговый чеклист по моделированию

1. **Всегда создавайте таблицу-календарь** для корректных временных фильтров
2. **Располагайте модель "сверху вниз":** справочники выше, факты ниже
3. **Активная связь — одна на пару таблиц**; вторую делайте неактивной
   и включайте через `USERELATIONSHIP` в конкретных мерах
4. **Both — крайняя мера**, а не стандартная настройка
5. **Фильтруйте, группируйте и подписывайте через поля справочников**,
   не таблиц фактов
6. **Скрывайте FK и технические ID** от конечного пользователя отчёта
